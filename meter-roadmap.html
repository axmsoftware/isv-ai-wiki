Development roadmap

Village Metering · three primary phases · working draft · not a standards schedule

ISV Tech Comm sequences Village Metering work so we do not mash prepaid field reality, sovereign mini-grid software, and utility grid programs into one pile. Ask of every feature: which phase? If the answer is “all three,” cut scope.

Discipline

Phase 1 keeps operators billing on gear that already exists. Phase 2 builds the open mini-grid core (Street-EMS / OpenAMI). Phase 3 adds grid-arrival and aggregator paths (2030.5, OpenADR, 1547). PAC workshops ≈ Phase 1 + a thin Phase 2 slice.

Phase 1

Installed-base interop

Talk to meters, gateways, and backends villages already run — without rewriting billing for every OEM.

  • STS / OpenPAYGO token path
  • DLMS/COSEM + ICD mapping
  • Modbus / ATM90 feeder boards
  • VMRS as read checklist
  • Open HES / ThunderCloud / MPM
Phase 2

Next-gen microgrid core

Islanded or weak-grid village OS: multi-tenant pole, actionable telemetry, local assemble & repair.

  • Street-EMS / MeshEMS
  • OpenAMI MQTT northbound
  • Feeder loss visibility
  • Cloudless edge rules
  • SIP (RFC 3261) control dialogs — only if proven needed
Phase 3

Next-gen grid connectivity

When the main grid or a DER aggregator arrives — utility-facing programs, not year-one prepaid.

  • IEEE 1547 interconnection
  • IEEE 2030.5
  • OpenADR VTN/VEN
  • SunSpec DER northbound

Phase 1 · Installed-base interop (detail)

Goal: operators keep collecting revenue and controlling disconnects while open stacks learn to speak the same southbound dialects. “Legacy” here means installed base — STS and DLMS are not obsolete; they are the field.

TrackWhat “done enough” looks like
Prepaid / tokens STS or OpenPAYGO vending path documented per site; token path stays separate from scheduled meter reads.
Meter readout Gateway (or HES) can read VMRS-tier registers from at least one DLMS and one Modbus/ATM90 path; ICD gaps listed honestly.
Operator backend At least one open HES/MPM-class system runnable without proprietary cloud lock — see ThunderCloud update below.
Hardware kits COTS or open PCBs (MeshEMS, CircuitSetup, DitroniX, DIN Modbus) assembleable in-country; license/credit clear before fab advice.

Update · ThunderCloud open under EarthSpark

Status (Aug 2026) — developer preview, not production

EarthSpark published ThunderCloud (and related repos) for open development. The public main branch is being restored to a stable, releasable build after a large modernization. Upstream README: not for live customer metering or billing until that milestone lands. Source: OSEA Discord development channel (Jul–Aug 2026) · github.com/EarthSpark/thundercloud (Apache-2.0).

ThunderCloud (cloud deploy) / GroundBolt (base-station deploy) is the open lineage of the SparkMeter operator application. Tristan (SparkMeter co-founder; ThunderCloud engineer) and EarthSpark describe the public work as follows — paraphrased from OSEA Discord, not a formal EarthSpark release note:

  • 1.x (not released as open “stable”) — Python 2; tight coupling to historical SparkMeter centralized services; hard to maintain in the open.
  • 2.0 modernization (public now) — Python 3; dependency upgrades; Chef → Ansible; Salesforce/Consul/databags → encrypted GitOps; Postgres upgrade; RabbitMQ/Celery and mmonit removed; build pipelines workable in public.
  • Near-term goal — get main to a stable, releasable ThunderCloud someone could run in production; then add the decade of deferred features. Current focus called out in Discord: Ansible converge from scratch (finish/merge half-done PRs); SymmetricDS container CI so sync can be tested without the full ThunderCloud stack.
  • Open design question (community) — meter control today behaves like a soft-loop / digital-twin drift repair (desired state in DB → driver/SparkNet HTTP → observe → repair), not a hard request→correlated response job ID. Correlation / in-flight job semantics under discussion on OSEA.

Credits called out publicly: EarthSpark team, Tristan, OpenAMI groundwork and lobbying, A2EI support, EnAccess/OSEA coordination. ISV maps this under Phase 1 — open operator software for the installed mini-grid base — complementary to MPM and to Phase 2 Street-EMS / OpenAMI MQTT.

Phase 2 · Next-gen microgrid core (sketch)

Street-EMS / MeshEMS, OpenAMI MQTT + VMRS-shaped payloads, feeder/branch/customer loss visibility, in-country kit assembly. IETF SIP (RFC 3261) only as an optional control-plane dialog layer once Phase 1 backends and Phase 2 telemetry are real — not a substitute for STS or DLMS. Detail lives on OpenAMI and MeshEMS.

Phase 3 · Next-gen grid connectivity (sketch)

Utility and aggregator programs after “grid arrival”: IEEE 1547, IEEE 2030.5, OpenADR, SunSpec DER northbound. These are deferred, not dismissed — see Standards. Village prepaid priority stays Phase 1–2 until a site has a real VTN/aggregator counterpart.
